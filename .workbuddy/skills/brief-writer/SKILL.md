# Brief Writer

## 目的

把"客户说的一句话"变成一份下游 Agent 能直接开工、且能量化验收的结构化 Brief。禁止把未澄清的口语直接传给创意或执行。

## 使用时机

- T2 策略阶段开始前，收到客户原始需求或 scout 的寻源输入。
- Lead 委派任务时，需要把模糊请求变成带验收口径的任务卡。

## 工作流程

1. **读取上下文**：先读 `AGENCY.md`、`01客户档案/`、相关 `00品牌资产/`。缺失资料标注"未提供"，不臆造。
2. **最多问 3 个澄清问题**：只在会改变输出方向时提问；否则用明确假设继续，并在假设区列出。
3. **产出结构化 Brief**，写入 `02进行中/<项目代号>-Brief-vN.md`，包含以下固定字段：
   - 项目代号 / 版本 / 日期
   - 业务目标（可度量）
   - 目标受众（人群 + 场景 + 当前认知）
   - 单一主张（对谁说 / 说什么 / 为什么说）
   - 硬性约束（预算、法务、品牌红线、排期）
   - 验收口径（怎么算达标）
   - 依据来源（文件名 + 段落；无依据写"未找到确凿依据"）
   - 置信度 / 待确认项
4. **提交 G2 闸门**：把 Brief 路径与待拍板项回报 Lead；人未放行前，不得进入 T3。

## 输出模板

```markdown
# Brief｜<项目代号> v<N>
- 日期：
- 业务目标：
- 目标受众：
- 单一主张：对<谁>说<什么>，因为<理由>
- 硬约束：
- 验收口径：
- 依据来源：
- 置信度：高/中/低
- 待确认项：
```

## 禁止事项

- 不写"大概""可能"而不给置信度。
- 不把客户没说过的数字、法条、引用写成事实。
- 不替人拍板方向；只把选项摆到闸门上。
